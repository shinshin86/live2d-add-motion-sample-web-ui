# AGENTS.md — Guide for AI Agents

A project that adds motions to a Live2D model using JSON only, with a WebUI
to verify playback. This document is the working playbook for AI agents
(Claude Code / Codex, etc.).

## The typical request, and what to do

Assume the user does not know the internal steps. The typical request is just
**"Add motions to this model"** (+ the path to the model's zip/folder).
In that case, execute the following autonomously:

1. **Locate the model** — if no path was given, search `local-assets/` and the
   repository for `*.model3.json`. If nothing is found, ask the user where the
   model is (only the user knows that).
2. **Set up** — `python3 tools/setup_model.py <zip or folder>`. A working copy
   is created under `models/` and registered in `model.config.json`. Every
   tool and the WebUI read that config from then on.
3. **Analyze** — `python3 tools/analyze_model.py` to learn the available
   parameters, their safe value ranges, the physics outputs (marked ★), and
   the base pose.
4. **Design motions** — following the "Design rules" below, write
   `motion-defs/<model>.py` for this model. The model name is the model3.json
   file name without its extension (e.g. `mao_pro.model3.json` →
   `motion-defs/mao_pro.py`). See the bundled sample
   `motion-defs/hiyori_pro_t11.py` for the format. Parameter sets differ
   between models, so design from the analyze output instead of reusing
   another model's definitions. If a definitions file for *this* model
   already exists (e.g. the bundled Hiyori sample), reuse or extend it
   rather than writing a new one.
5. **Generate** — `python3 tools/gen_motions.py` (generate + register into
   model3.json; idempotent). Referencing a parameter the model does not have
   fails here.
6. **Validate** — fix issues until `python3 tools/validate_motions.py` exits 0.
7. **Visual check** — take screenshots with `tools/verify_browser.sh` and
   confirm with your own eyes that the expressions and poses look right
   (if the character stays in the base pose, playback failed).
8. **Hand over** — start `python3 tools/serve.py` (add `--port N` if 8765 is
   taken) and tell the user to check http://localhost:8765.

Deciding *what* to make (which expressions are feasible, which parameters to
use) is the agent's job. Everything mechanical is done by the tools.

## Design rules (model-independent)

An optional `motion-defs/<model>.local.py` uses the same `define(curve, motion)`
format and appends local motions and expressions after the main definitions.
Duplicate names fail. Keep local definitions and their source data under the
git-ignored `motion-defs/` directory, never in the generated `models/` working copy alone.

- Never edit rigs/meshes in Cubism Editor. Use only the model's existing
  parameters.
- Keep values within the ranges observed in the existing motions
  (`analyze_model.py` prints them; the validator enforces the same rule).
- The final frame must return to the base pose (estimated automatically from
  the first frames of the existing motions; defaults differ per model —
  e.g. Hiyori's MouthForm rests at 1).
- Never animate physics output parameters (marked ★) directly. Move the
  head/body angles and hair etc. will sway naturally.
- Avoid PartOpacity switching in principle: it produces unnatural
  fade-ins/pops.
  - If you do need it (e.g. a model whose raised-arm pose is a separate
    part set), put every PartOpacity curve **after** all Parameter curves
    in the motion's `Curves` array. The Cubism SDK evaluates curves grouped
    by target in that order, so any Parameter curve placed after a
    PartOpacity curve is silently skipped: the part switch works, but the
    motion otherwise stays at its t=0 pose. The validator does not catch
    this — only the visual check does.
- Register new motions into the `Action` group; never change the existing
  groups.
- Actions use `Loop: false` with FadeIn/Out of 0.2–0.5 s.
- Exception: **loop motions** (`motion(..., loop=True)` + `curve(..., loop=True)`),
  e.g. an emotion held while the character speaks. See README "Loop motions".
  - Every curve ends on its first value; the generator gives the keys
    periodic tangents so the speed carries through the seam. They do not
    need to start/end at the base pose (the validator checks the seam
    instead: same value and same slope at both ends).
  - Put seams mid-swing, not at extremes: if every curve is at rest at the
    seam, the loop visibly stops for a moment each cycle.
  - Give all oscillating curves periods of Duration/n so they meet at the seam.
  - Leave the LipSync parameters (`analyze_model.py` lists them) out, and
    bake blinks into the EyeOpen curves (auto-blink pauses during motions).
  - The Cubism Framework ignores `Meta.Loop`: the player must call
    `setIsLoop(true)` and `setIsLoopFadeIn(false)` before starting it.
    `index.html` (`playMotion`) is the reference implementation.
  - Verify with `tools/verify_browser.sh --loop Action:<n>`: the shots on
    both sides of each seam must match and still show the loop's expression.
- Arm/hand parameters are often hard to interpret. If no natural continuous
  parameter can be confirmed, skip large arm gestures and express with the
  face and body instead.
- Without reference motions, generation/validation use conservative conventional
  ranges/base poses for known standard IDs (angles ±30, eye open 0–1,
  eye balls ±1, ...). Custom IDs need observed ranges. Be extra thorough with
  the visual check; conventional ranges do not establish a rig's actual limits.
- Do not keep an unnatural motion: explain why and propose an alternative.

## Portable shared motions

`motion-defs/shared/<pack>.py` is tracked and uses `define(curve, motion)` returning
`(MOTIONS, MANIFEST)`. Values are normalized: 0 = estimated base, -1 = safe lower
bound, +1 = safe upper bound, scaled separately on each side of the base. For
instance MouthForm -0.5 maps to -0.5 with base 1 and range [-2,1]. One-shots
start/end at normalized 0; loops set loop=True on both curves and motion.

Select with a module-level declaration in the main or optional local model file:
`SHARED_MOTIONS = {"gestures": {"nod": {}, "shakehead": {}, "surprised": {}}}`.
No declaration means no shared motions. Local options merge over main options;
False disables an entry. Options: name (ASCII file stem), label (display text),
scale (finite [-1,1], negative reverses direction), parameters (source ID →
target ID, or None to skip; keys must exist in that template).

Use shipped-motion ranges/base poses, conservative standard-ID fallbacks only
when absent. Missing parameters, physics outputs and unknown ranges are skipped
with a note; no usable curves fails. Never guess custom ranges or drive physics
outputs. Preserve existing model/local definitions; shared samples append after
them and recordings so prior Action indices stay stable. Collisions among all
three sources, among shared outputs, or with unmanaged motion files fail before
writes. Keep `.generated-shared-motions.json` with the working model: it records
owned files, including unselected remnants, which generator/validator exclude
from reference analysis. Opting out unregisters but leaves the old file.

The bundled pack adapts nod, head shake and surprise from Hiyori. Keep the
original model-specific motions too, and visually verify shared samples on both
models; normalization does not guarantee the same expression on every rig.

## Discovering model-specific quirks (lessons from Hiyori as an example)

How a parameter "reads" differs per model. Learn from how the existing
motions use them. Hiyori examples:

- The smiling-arc eyes (^^) come from **EyeOpen=0 combined with EyeSmile=1**
  (raising Smile while EyeOpen=1 barely changes anything). Discovered from
  the combination patterns in the existing motions.
- The resting MouthForm is 1 (not 0). The surprised "o" mouth is around -1.5.
- Yaw (AngleX) reads subtly; a head shake needs ±20 or more to be legible.
- Idle motions park the arms (ArmLA/RA=-10), so moving the arms in an action
  easily breaks continuity with the surrounding idle.
- Hiyori's brows are hidden by bangs and its existing motions provide no angry
  brow pose. The model-specific sample expression is `sleepy` ("ねむい"), not anger:
  EyeOpen multiplied by 0.5, low brows and MouthForm=0. Clear EyeSmile and Cheek
  to avoid inheriting a smile or blush. MouthForm=-1 leaves a small "o" even with
  MouthOpenY=0. Confirm brow angles and forms together in actual renders; do not
  copy another model's signs or insist on an expression the rig cannot convey.

For a new model, rediscover this kind of quirk from how its existing motion
curves use the parameters.

## Expressions

`define(curve, motion)` may return `(MOTIONS, MANIFEST, EXPRESSIONS)`; the older
2-tuple still works. `EXPRESSIONS` maps an ASCII file stem to a dictionary with
`parameters: [(ParameterId, value, blend), ...]`, optional `label` (defaults to
the stem), `fade_in` and `fade_out` (both default to 0.4 seconds). Blends are
`Add`, `Multiply` and `Overwrite`; labels must be unique.

Generation writes `expressions/<stem>.exp3.json` and registers
`FileReferences.Expressions`. The generated `.generated-expressions.json`
sidecar in the runtime directory records ownership: keep it with the working
model. Only exact owned registrations are replaced; shipped entries/files are
preserved and conflicting names/files fail. Removing a definition unregisters
it but leaves its generated file on disk. The independent validator checks all
registered expressions, including schema, finite values, blends, parameter IDs,
physics outputs, and resulting values at the estimated base pose. It uses
observed ranges or conservative conventional ranges for standard IDs; custom IDs
without a reference range fail.

The control page lists expressions in the motion tab. One selection is active;
click it again or use "表情リセット" to fade out. The layer runs after blink/face
tracking and before lip sync, without saving back into the motion pose. Keep
LipSync parameters out when designing talking expressions. Expressions do not
need to start/end at the base pose. Selection/clear on index.html, including the
expression query hook, is relayed to stream.html when relayOn is enabled.

Verify each expression alone and over an Action, plus loop/speech coexistence:
`OUT=tmp-verify/<case> tools/verify_browser.sh --expression <stem> [Action:n] [seconds]`.
`OUT` selects the folder cleared of PNG files on each run. Inspect the screenshots
and check switching/reset fades in the browser; a static screenshot alone cannot
prove the fade. `?expression=<stem or exact Name>` applies on load.

### Portable shared expressions

Shared packs may return `(MOTIONS, MANIFEST, EXPRESSIONS)`; two-item packs still
work and an expressions-only pack returns `({}, [], EXPRESSIONS)`. Select with
`SHARED_EXPRESSIONS = {"faces": {"smile": {"name": "smile"}, "shy": {"name": "shy"}, "surprised": {}, "glare": {}}}`
in main/local model definitions. This selection is independent of SHARED_MOTIONS;
local options merge over main options and False disables. The same name/label/
scale/parameters options apply. Default stems are `shared_<pack>_<expression>`;
labels always start with `共通: `, including overridden labels.

Overwrite/Add use normalized finite values in [-1,1]. Multiply n by scale first,
then map the target to base + n*(hi-base) for n>=0, base + n*(base-lo) otherwise.
Overwrite emits that target; Add emits target-base, retaining additive blending
over motions. Multiply uses a finite plain factor, scaled as
1+(factor-1)*scale. Scale is finite in [-1,1]; 0 is neutral, negative reverses the
change. Clamp each blend's result at the base pose to the safe bounds, printing
a note and adjusting the emitted value/factor. Runtime still clamps to rig limits.

Use the same observed references/conventional fallbacks as shared motions.
Missing IDs, physics outputs and custom IDs with unknown ranges are skipped with
a note; no usable parameters fails. Remapping keys must exist in the template;
duplicate source/target IDs fail. Name, label and file collisions with model/local,
other shared or shipped expressions fail before writes. Shared and model expressions
share `.generated-expressions.json`: retain it, including ownership of unselected
remnants. Opting out unregisters expressions while retaining their files. Existing
Action indices and unrelated expression files/registrations must stay unchanged.
Registration/UI order is shared selections first, then preserved shipped entries
(same relative order), then model/local definitions. Moving an owned model expression
to the shared pack can reuse its stem via name: old owned registrations are replaced
even when their labels change. Do not relax checks for unmanaged files or shipped
registrations. Retain the ledger, including earlier ownership records.

`faces.py` provides smile, shy, surprise and sideways half-closed eyes, visually
checked on both Hiyori and Haru. The samples keep smile/shy file stems with name
overrides, so `?expression=smile` / `shy` still work; labels use `共通: `.
Remove their old model definitions; only Hiyori sleepy and Haru angry remain
model-specific. Do not add closed_smile: smile already gives the same ^^ eyes.
Smug, troubled and stronger embarrassment
did not read consistently using their common IDs; do not restore them without
new visual evidence. Haru has no ParamCheek: map it to ParamTere (observed [0,1],
base 0) in its smile/shy selections. Smile also skips BrowLY/RY in Haru to keep
its original motion-driven brows. The shared smile uses blush 0.45 between the
previous 0.5/0.4 values. Shy uses normalized brow targets and MouthForm Multiply
0.3; both sample models rest at 1, preserving the resting mouth while allowing
motion changes. Visually check these adaptations over actions as well as at rest.
Other Haru-only tear/eye-form IDs are not part of this shared pack.
Surprise sets MouthOpenY for a visible open mouth;
lip sync has priority over this value during speech. Check each expression alone
and over an Action on every opted-in model, plus switching/reset and loop/speech
coexistence. The existing expression query hook accepts shared stems and labels.

### Expression relay

`POST /live/send` accepts `{"type":"expression","name":"<file stem>"}` or
`name: null` to clear. Use the registered File basename without `.exp3.json`,
not its index or display label. The ID uses ASCII letters/digits/_/- (1–240 chars).
Only type/name fields are accepted. Invalid values/paths are rejected on server
and client; unknown or ambiguous IDs are ignored by the streaming renderer with
a diagnostic under `?status=1`. Keep the current expression on an unknown ID.

The server keeps the latest expression message in memory under clients_lock and
replays it to new/reconnected `/live/events` subscribers, registering each queue
and queuing its snapshot in the same lock to preserve order. Clear/model switches
reset that state; server restart forgets it. Model notifications clear expressions
even on explicit-model streams, which otherwise stay on their pinned model. No
expression snapshots go to `/live/commands`; no one-shot motion replay is added.
Control-page model reloads remove `?expression=` so it cannot reapply the old selection.
`GET /live/status` advertises `expressionRelay: 1`.

Busy pose messages may be dropped; expression/motion/stop commands retain FIFO
order in the sender, server and streaming page's asynchronous loading queue.
Event queues limit pose backlog to 64 and retain discrete commands beyond that;
external-command queues are unchanged. In stream.html, attachExpressions runs
after the face driver and before lip sync, preserving the same blend/fade behavior
as index.html. Recording previews and placement remain local. Old receivers ignore
the unknown expression type. Restart the server and reload both pages after updates.

Verify apply/clear and late join on both models with one headless Chrome at a time;
drive `/live/send` externally while stream.html is open. Also check unknown IDs on
explicit-model streams, model-switch clear, invalid requests and command ordering
under pose backlog. Screenshots alone cannot prove fades; retain the blend/fade
tests and check switching/reset in a browser.

## Switching installed models

`GET /live/models` lists `models/*/*.model3.json` and the current model name
(`null` if the config is missing or invalid). Same-origin JSON
`POST /live/model` with `{"name":"<installed name>"}` atomically updates
`model.config.json` under `recordings_lock`; it requires a localhost/127.0.0.1
Host and returns 404 for unknown names. It notifies both `/live/events` and
`/live/commands` with `{"type":"model","name":"..."}`. This type is not
accepted by `/live/send`. `GET /live/status` advertises `modelSwitch: 1`.

The control panel shows a selector when at least two models are installed.
Local switching is blocked during recording, saving, or while a recording
is unsaved. Control pages reload without their `model` query on a model
notification; streaming pages reload only without an explicit `?model=`.
Restart the server and reload pages after updating this feature.
Never use `setup_model.py` to switch installed models: it replaces the working
copy and removes generated motions. Change the config through `/live/model`
instead; generation, validation, and recordings then use the selected model.

## Saving camera recordings

The save form shows only the title input (Japanese allowed, up to 40 characters,
initially empty and focused after recording stops). An empty title uses the
recorded date (`録画 M/D HH:MM`) as `label`. The automatically assigned ASCII
file name (`rec_YYYYMMDD_HHMMSS`) is inside initially closed
"詳細設定(ファイル名)"; saving errors open these settings. New recordings include `recordedAt`
in ISO 8601 with the local UTC offset; it is optional for older sources.
Saved-motion buttons show `entry.Name` above the recorded date (`録画 M/D HH:MM`),
loaded from the recording JSON. Missing/invalid dates fall back to the timestamp
at the end of the file name, then the file name itself. Never rewrite old recordings
just to change their displayed metadata.

With `tools/serve.py`, `POST /recordings` saves the source JSON, then runs
`gen_motions.py` and `validate_motions.py` using the current Python interpreter.
Saving and regeneration are serialized. `GET /live/status` advertises
`recordingsVersion: 2`; the current recording client checks this before saving
and asks for a server restart/force-reload on mismatch. Restart the server and
force-reload the page after updates. A successful reply includes `ready: true`;
the WebUI offers "再読み込みして表示" to reload the model and open the saved-motion
list. If either command fails, the source JSON is kept, the page shows an error,
and the server prints details. Fix the cause and run generation/validation before
reloading. A plain static server keeps the download fallback and requires these
commands manually.

## Editing saved recordings

Version 1 recording sources may include optional
`edit: {trimStart, trimEnd, speed, smooth, loop}`. Trim bounds are positions in
the original source in seconds (end is not a length to remove); defaults keep
the full duration. Speed is 0.25–4, smooth is 0–1 and loop defaults to the source
flag. The edited duration must be at least one 30 fps frame. `tools/recording_edits.py`
trims, blends samples with a centered 11-frame moving average, then resamples
speed at 30 fps before the generator's existing easing/seam/key-reduction steps.
Raw params and source metadata are never changed. Sources without edit retain
the legacy output exactly. Both preview and generation use this processing.

`GET /live/status` adds `recordingEdit: 1` (recordingsVersion stays 2).
`POST /recordings/preview` and `/recordings/edit` accept `{model, id, edit}`;
`POST /recordings/delete` accepts `{model, id}`. All recording POSTs require the
server's localhost/127.0.0.1 Host with port and same-origin JSON (external apps
may omit Origin), and share recordings_lock with saves and model switching.
Preview returns `{motion}` without writes. Edit atomically saves only the edit
metadata, then generates/validates; failures retain the saved settings, like
recording saves. Deletion temporarily hides source and generated output, restores
both on failure, and regenerates/validates. Removing the generated output avoids
mistaking an orphan recording for an original reference motion.

Saved-motion entries have an edit button. The editor supports preview, stop,
save/reload, reset to original settings, and an inline delete/cancel confirmation
(never browser confirm()). Preview plays transient data only on index.html,
pausing camera/lip-sync contributions there; the relay continues independently.
It is not sent to OBS. Unsaved edits or an in-flight operation block local model
switches; finish/close editing before recording again. Restart the server and
force-reload pages after updates. `?editrecording=<ID>` opens the editor on load.
Always test on a copy of an existing source, remove that copy afterward, and
verify the user's original recordings are byte-for-byte unchanged.

## Upper-body tracking

The camera tab's body toggle starts OFF on every load. `web/body-camera.js`
shares the current video with a separate CPU Pose Landmarker Worker; it never
opens a second camera or waits in the face capture path. `body-worker.js` uses
the same pinned 0.10.21 runtime and local `pose_landmarker_lite.task`, no masks,
at most 10 fps, one bitmap in flight, with extra backoff after slow inference.
Failure disables only body inference; the face Worker continues. Stop/disable
terminates the body Worker and late bitmaps are closed.

`body-tracking.js` requires finite, nondegenerate shoulders 11/12 with visibility
>=0.6; presence is checked only when supplied (the pinned JS API omits it).
Shoulders alone provide yaw from world depth and roll from the image shoulder
line. Hips 23/24 are optional: only pitch requires confident hips and a valid torso
length. Missing hips drop pitch and retain shoulder yaw/roll. First valid shoulders
calibrate yaw/roll; first valid hips calibrate pitch independently, avoiding a jump
when hips enter the frame. The reset button recalibrates visible axes. Lost poses
expire after 500 ms, then fade out their contribution.

Raw body yaw/pitch/roll use timestamped One Euro filters (minimum cutoff 0.65 Hz,
beta 0.15 per degree/second, derivative cutoff 1 Hz). Filters reset on calibration,
reset and loss; hips calibrate independently when they return. Render-clock body
smoothing uses max(face tau, pose interval × (0.85 + smoothing)); default smoothing
0.35 gives 1.2 pose intervals. The interval is an EWMA of valid result gaps, clamped
to 16–500 ms; inference remains at most 10 fps. Synthetic body results also run at
most 10 fps. Run `node tools/test_body_tracking.mjs` for jitter, ramp lag, glide,
loss, calibration and signed-bound checks.

Body sensitivity is independent of head sensitivity: 0.25–3, default 1. Axis gains
are yaw 0.7, pitch 0.65 and roll 1.15 per measured degree. Share mirror/smoothing;
mirror yaw/roll only. Add independently weighted face-derived body sway rather
than replacing it, then clamp the effective composed contribution before encoding
the existing single relay weight. Account for the Live2D pitch/roll sign inversion
when clamping asymmetric bounds. Arm and rig-specific shoulder controls stay unused.

`web/body-model.js` loads read-only `GET /live/body-ranges?model=<model3 path>` once
per page/model with a 2 s timeout. The server accepts only exact installed model
paths, reads under recordings_lock, uses observed_reference (excluding Actions and
all shared-owned remnants), and returns base/min/max/source for body XYZ, disabling
physics outputs. Unknown paths return 404, invalid references 500. No config or
model files are written. Missing observations use conventional [-10,10] bounds.
The client intersects with core bounds and skips absent parameters. Static/older
servers fall back to conventional bounds and show that source in the readout.
Hiyori XYZ references are [-10,10]/[-7,10]/[-10,10], base 0; Haru uses [-10,10]
on all axes. Contributions are relative to the reference base. Both control and
stream face drivers also clamp motion + tracked body to absolute safe bounds when
optional bodyAngleY marks a combined body pose; face-only/legacy behavior stays as is.

Combined face/body parameters keep independent loss weights and enter the same
renderer, recorder and relay. Optional bodyAngleY maps to ParamBodyAngleY with
the pitch sign reversed, and is omitted when body tracking is off. Old messages
and recordings need no new fields/version; new relay readers accept either and
allow bodyAngleY within the same defensive ±30 envelope as other angle fields.
Keep encoded combined body values inside that envelope even during loss fades.
Reload both pages after updates. Lock the body toggle during recording so every
sample has the same parameter IDs. Never transmit images or raw pose landmarks.

"キャラ全体を動かす" is optional, defaults OFF on every load and is disabled while
body tracking is OFF. Translation/rotation strengths range 0–2, default 1. The
shoulder midpoint is relative to its calibrated neutral, in units of the neutral
shoulder width (Y also accounts for image aspect). Filtering uses One Euro
minimum 0.65 Hz / beta 8 for normalized positions plus the same body-time glide;
rotation uses the filtered body roll. Mirror flips X and rotation only. Final
viewport-relative caps are X ±0.15, Y ±0.08 and rotation ±8 degrees. Loss fades
with the body weight; calibration resets all offsets. `web/body-stage.js` applies
a transient parent transform around the user's placement anchor on both pages;
drag/wheel/reset and stream placement storage contain only the base placement.
The movement is live/stream only: recordings keep only rig parameters.

Pose relay messages may include `stage: {x, y, rot}` with final weighted offsets.
Server and client reject malformed, nonfinite, extra-field or out-of-bound stage
objects; old senders omit stage and clear any previous offset, old receivers
ignore the field. Only final numbers are sent, never images or landmarks. Busy
pose dropping stays unchanged. Stream offsets fade after 1 s without a pose,
independently of face weight, and clear on model notifications. Run
`node tools/test_body_stage.mjs` and `python3 -B tools/test_body_stage.py` for
geometry, caps, mirror, loss, placement storage and relay checks.

`web/body-debug.js` renders opt-in local diagnostics at most 5 Hz only while the
"数値を表示" checkbox is checked. Default OFF, never persisted; `bodydebug=1`
enables it on load. Include detection/mode/age, each shoulder/hip visibility and
weakest landmark, pose interval/fps, raw and filtered yaw/pitch/roll, calibrated
deltas, face sway, effective Live2D body XYZ encoded additive values,
weight/effective contribution, range source and effective stage x/y/rotation.
Diagnostics/landmarks never enter recordings or relay payloads; only the final
composed parameters and stage offsets do.

`?fakebody=1` supplies synthetic landmarks through the same math. `bodytime=N`
holds a synthetic time; body=0 disables its contribution, bodyhips=0 hides hips.
Add `bodystage=1` with fakebody to enable whole-character movement for verification.
Can combine fakeface, bodydebug and recording hooks. Verify OFF and opposite poses
on both models, including bodytime=±0.35 for small leans and ±1 for extremes;
compare prior images under tmp-verify/body/. Inspect the readout and shoulder-only
path, resulting body XYZ recording curves, and validate both models. Real-camera
accuracy, signs and face responsiveness still need a manual check. The model's
source, hash, license and pinned-runtime privacy notes are in vendor/mediapipe/.

## Streaming updates

Face sampling, recording and lip-sync levels run on `web/background-clock.js`
and its worker, independently of PixiJS animation frames. Rendering consumes the
latest pose. The synthetic face uses the same clock so background checks do not
depend on a main-thread timer. Only one worker tick and one relay POST may be in
flight; busy pose messages are dropped and motion/stop commands retain order.
`GET /live/status` includes the number of SSE `clients`. The control page polls
it to show connection and send errors. This counts SSE subscribers, including
diagnostic readers, and disconnect detection can wait for the next keepalive.
In headless Chrome, background tabs may still report `visible`: stop only the
control page's animation frames to test rendering independence. Freezing a whole
page also freezes worker delivery and is a different condition. Actual OBS and
minimized-window camera behavior still require a manual check.

## Streaming placement

`web/stream-view.js` adds the control page's drag and cursor-centered wheel/pinch
zoom to `stream.html`. Double-click resets to the initial URL placement (default:
center at x=0.5, y=0.55, relative zoom=1). Local storage uses a key per resolved
model3 URL and stores relative x/y plus relative zoom. Resizing reapplies these
values against the new fitted size. Actual scale stays within 0.05–5.
URL `zoom` (positive), `x` and `y` (0–1) override saved values per field; invalid
values are ignored. Storage errors must not prevent interaction. In OBS, use the
Browser source's "Interact" window. Keep streaming placement separate from the
control page and do not include it in relay messages.

## Motion shortcuts and external commands

`web/hotkeys.js` handles Action keys only on index.html. Defaults are 1–9 in
display order (one-shots, loops, recordings), 0 to stop, and Escape always stops
outside text input/assignment mode. Repeating the playing motion keeps it;
button clicks still restart it. Bindings use motion file stems, not indices,
and are saved per resolved model3 URL. Edited settings leave new IDs unassigned.

`tools/serve.py` accepts `POST /live/motion` with `X-Live-Token` or Bearer auth
and JSON `{"motion":"<ID or exact Name>"}` / `{"stop":true}`. IDs take precedence;
ambiguous names return 409, unknown names 404, missing/invalid tokens 401, and
no connected controller 503. A 204 means queued, not confirmed playback.
`GET /live/commands` is a separate SSE stream for index.html; do not change
the existing motion/stop formats on `/live/events`; expressions use the separate
expression message described above.
`GET /live/status` advertises `motionRemote: 1` and `controllers` (including
diagnostic subscribers; disconnection detection may wait for a keepalive).
`web/motion-remote.js` subscribes only when this capability is available.

`GET /live/token` reads the token; same-origin JSON `POST /live/token` rotates
it. Both token and motion endpoints require Host localhost/127.0.0.1 with the
server's port. `.live-token` is persistent, git-ignored, and blocked from static
serving: never commit or print it in reports. Restart the server and reload
the control page after updating these endpoints.

## WebUI debug hooks (index.html)

| Query | Effect |
|---|---|
| `?play=Action:0` | Auto-play the given motion after load |
| `&freeze=1.2` | Pin the pose at that many seconds after playback starts (rendering continues) |
| `?uitest=1` | Run a synthetic drag/zoom event test; results appear in the status bar |
| `?model=<path>` | Load the given model instead of model.config.json |
| `&cycles=3` | End a loop motion after its 3rd cycle |
| `&lipsync=1` | Simulated lip sync (overwrites the LipSync parameters every frame); `&lipsync=mic` uses the microphone |
| `&audio=<url>` | Lip-sync to an audio file (loudness of the playing audio) |
| `&expression=<name>` | Apply an exp3 expression by file stem or exact display name |
| `?fakebody=1&bodytime=0.35&bodystage=1` | Synthetic upper body plus live-only whole-character movement |
| `&editrecording=<ID>` | Open a saved recording's editor without changing its source |
| `&hold=N` | Keep the window "load" event pending for N s (used by verify_browser.sh; also on stream.html) |
| `&tab=motion\|camera` | Open a panel tab (the camera hooks open the camera tab unless `&tab=` says otherwise) |
| `&camera=1` | Start the camera on load |
| `&preview=0` | Start with the camera image hidden (tracking continues) |
| `&fakeface=1` | Drive the face with synthetic tracking results (no camera) |
| `&fakebody=1` | Drive body angles from synthetic shoulder/hip landmarks; bodytime=N fixes a pose, body=0 disables it, bodyhips=0 hides hips |
| `&bodydebug=1` | Show local body tracking diagnostics (default OFF; no camera auto-start) |
| `&record=N` | Record N seconds of the face and save it (`&recordloop=1`: as a loop, `&recordname=<name>`: motion name); with `&fakeface=1` this tests the recording path headless |
| `stream.html?bg=green&status=1` | Streaming page: background (transparent by default, `green`, `blue`, `<hex>`); `status=1` shows the relay state |

## Headless-browser verification pitfalls (measured; important)

`tools/verify_browser.sh` already handles all of these. If you roll your own:

- `--virtual-time-budget` does **not advance motion time** (playback stays on
  frame 0 with playing=true). Use real time + `--timeout=30000`.
- `--dump-dom` does not wait for `--timeout`; it dumps right after load.
  Check state via `--screenshot` images instead (the status bar text is
  readable from the image).
- WebGL fails to initialize with `--disable-gpu`. Use
  `--use-angle=swiftshader-webgl --enable-unsafe-swiftshader`.
- Screenshots are taken as soon as the window "load" event fires (about 2 s
  after start), which is before `&freeze=` kicks in. To verify "what it looks
  like at N seconds", pin the pose with `&freeze=N` and keep "load" pending
  with `&hold=N+4` (the page then requests `/__verify_hold`, which the
  script's own server answers only after that many seconds). Never rely on
  sleeps.
- Run **one headless Chrome at a time** and never pass a fresh
  `--user-data-dir`: concurrent instances hand off to the first one and exit
  without a screenshot, and on macOS a new profile shows Chrome's first-run
  "Welcome" dialog on the user's screen (even with `--no-first-run`). To check
  the streaming relay, open one page and drive or read the relay with
  `curl` / a small script (`POST /live/send`, `GET /live/events`).
- Camera checks headless: `--use-fake-device-for-media-stream
  --use-fake-ui-for-media-stream` gives a camera without a face, so it only
  proves that MediaPipe loads ("顔が見つかりません"); use `&fakeface=1` to check
  how faces drive the model. Real cameras need a manual check.
- If the canvas comes out blank: `PIXI.Application` needs
  `preserveDrawingBuffer: true` (already set in index.html). Freezing by
  stopping the ticker does not show up in screenshots — that is why freeze
  stops only the motion updates.

## Definition of Done

1. `validate_motions.py` exits 0
2. Every `verify_browser.sh` screenshot shows the intended expression/pose
   (still in the base pose = playback failed; no artifacts or unnatural fades)
3. Existing motions, groups and shipped expressions are untouched (the model3.json
   diff is the Action group + generated Expressions only)
4. The user has been given the local-server URL to check
